# 🧠 Feature: Obsidian Vault Integration

## 1. Feature Description

### Feature name

**Automatic Obsidian Vault Integration for Runbooks & Notes**

### Goal

Allow the Django Teacher Agent to automatically save generated learning material into the user's Obsidian vault.

Instead of:

```text
Agent generates runbook
        ↓
User copies response
        ↓
User opens Obsidian
        ↓
User creates folder
        ↓
User creates .md file
        ↓
User pastes response
```

we want:

```text
User asks Django question
        ↓
Django Teacher Agent
        ↓
Generates explanation / debugging runbook
        ↓
Obsidian Integration
        ↓
Creates folder if needed
        ↓
Creates .md file
        ↓
Saves runbook
        ↓
Obsidian Vault
```

The user could then see something like:

```text
My Obsidian Vault/
│
├── Django/
│   ├── Concepts/
│   │   ├── Django ORM.md
│   │   ├── Views.md
│   │   └── URL Routing.md
│   │
│   ├── Debugging/
│   │   ├── TemplateDoesNotExist.md
│   │   └── Migration Errors.md
│   │
│   ├── Security/
│   │   └── CSRF.md
│   │
│   └── Architecture/
│       └── Django MVT.md
│
└── Runbooks/
    ├── Django ORM.md
    └── Debugging Migration Error.md
```

# 2. What technologies should we use?

I would split this into **core technology** and **future technology**.

## 🟢 Core MVP

Use:

- **Python**
    
- **Markdown (`.md`)**
    
- **JSON configuration**
    
- Python filesystem APIs (`pathlib`)
    
- Your existing Django Teacher Agent
    
- Existing runbook system
    

### Why Markdown?

This is perfect for Obsidian.

Obsidian's notes are fundamentally Markdown files:

```text
My Note.md
```

So you don't actually need a special Obsidian API just to create notes.

Your Python code can do:

```python
Path(vault_path / "Django" / "Concepts" / "Views.md").write_text(...)
```

That's enough for Obsidian to recognize the note.

---

# 3. Where does JSON fit?

JSON should **not contain the actual runbook**.

Instead, use JSON for configuration.

For example:

```json
{
    "enabled": true,
    "vault_path": "C:/Users/Tim/Documents/MyVault",
    "base_folder": "Django",
    "runbooks_folder": "Runbooks"
}
```

Or potentially:

```json
{
    "enabled": true,
    "vault_path": "C:/Users/Tim/Documents/MyVault",
    "folders": {
        "concepts": "Django/Concepts",
        "debugging": "Django/Debugging",
        "security": "Django/Security",
        "architecture": "Django/Architecture"
    }
}
```

This gives your agent a configurable destination without hardcoding:

```python
C:/Users/Tim/Documents/MyVault
```

into the application.

### Important distinction

```text
JSON
 ↓
configuration
```

while:

```text
Markdown
 ↓
actual Obsidian notes
```

# 4. Where does MCP fit?

This is where I would be careful.

### You don't need MCP for MVP.

You can implement:

```text
Django Teacher Agent
        ↓
ObsidianService
        ↓
Python pathlib
        ↓
Markdown file
        ↓
Obsidian Vault
```

This is actually **simpler and more reliable** for the first version.

---

## MCP can become Phase 2

MCP becomes much more interesting when you want the agent to **interact with the vault**, rather than simply write a file.

For example:

> "Find my previous Django ORM notes."

or:

> "Update my Django ORM runbook with this new information."

or:

> "Find everything I know about Django authentication."

Then your architecture could become:

```text
Django Teacher Agent
        ↓
MCP
        ↓
Obsidian tools
        ↓
Vault
```

Potential tools:

```text
create_note()
read_note()
update_note()
search_notes()
list_notes()
create_folder()
```

So I would plan MCP as a **future extension**, not make it a dependency of the first implementation.

# 5. Proposed Architecture

I'd design the feature around an **Obsidian integration/service layer**.

```text
                 Django Teacher Agent
                         │
                         ▼
                 Runbook Generator
                         │
                         ▼
                Runbook / Note Object
                         │
                         ▼
                ObsidianService
                   │          │
                   │          │
                   ▼          ▼

                   │          │
                   └────┬─────┘
                        ▼

                        │
```

This is important because you don't want your runbook generator to contain code like:

```python

```

everywhere.

Instead:

```python

```

The integration becomes its own component.

# 7. What each new file does

## `config/obsidian.json`

Stores configuration:

```json
{
    "enabled": true,
    "vault_path": "C:/Path/To/Vault",
    "base_folder": "Django"
}
```

---

## `integrations/obsidian/config.py`

Responsible for loading and validating configuration.

Conceptually:

```python
config = load_obsidian_config()
```

It should check things like:

- Is integration enabled?
    
- Does vault path exist?
    
- Is it actually a directory?
    
- What is the base folder?
    

---

## `integrations/obsidian/service.py`

This becomes the main interface.

Something like:

```python
class ObsidianService:

    def save_runbook(self, runbook):
        ...

    def save_note(self, note):
        ...

    def create_folder(self, folder):
        ...
```

Your teacher agent doesn't need to know how the files are created.

It just says:

```text
save this runbook
```

---

## `formatter.py`

Converts the generated runbook into valid Obsidian Markdown.

For example, the agent produces:

```text
Title: Django Migrations

Explanation:
...

Example:
...
```

The formatter turns that into:

```markdown
# Django Migrations

## Explanation

...

## Example

...
```

Later, this is also where you could generate:

```yaml
---
type: runbook
topic: Django Migrations
category: debugging
created: 2026-08-10
tags:
  - django
  - migrations
---
```

That's called **YAML frontmatter**, and Obsidian supports it.

---

# 8. `file_manager.py`

This is responsible for the actual filesystem operations.

For example:

```text
create folder
       ↓
check whether file exists
       ↓
create/update file
```

It could provide:

```python
create_directory()
create_file()
update_file()
file_exists()
```

This separation is useful because later you could replace the filesystem implementation with an MCP implementation without rewriting the entire teacher agent.

# 11. Filename generation

You should also plan this carefully.

For:

> Explain Django class-based views

you could generate:

```text
Django Class Based Views.md
```

For:

> Fix TemplateDoesNotExist

you could generate:

```text
TemplateDoesNotExist.md
```

You need a filename sanitizer to handle characters that Windows doesn't allow.

For example:

```text
Django: URLs? Explained!
```

might become:

```text

```

# 12. What happens if the file already exists?

This is an important requirement.

You don't want:

```text
Django ORM.md
Django ORM (1).md
Django ORM (2).md
Django ORM (3).md
```

every time the agent explains ORM.

I would plan three possible behaviors:

### `create`

Only create a new file.

### `update`

Update an existing note.

### `overwrite`

Replace the existing note.

For the MVP, I'd recommend:

```text
File doesn't exist
    → create

File exists
    → don't destroy it automatically
    → report that it already exists
```

Then later add intelligent updating.

# 15. Proposed implementation phases

I'd break the feature into **5 phases** rather than trying to implement everything at once.

## Phase 1 — Basic Obsidian Export

Goal:

> Save a runbook as `.md`.

Implement:

```text
obsidian.json
ObsidianService
Markdown formatter
File manager
```

Flow:

```text
Runbook → Markdown → .md → Vault
```

---

## Phase 2 — Automatic Organization

Add:

```text
Concepts
Debugging
Security
Architecture
Best Practices
```

and automatically create folders.

```text
Django/
├── Concepts/
├── Debugging/
├── Security/
├── Architecture/
└── Best Practices/
```

---

## Phase 3 — Obsidian Metadata

Add:

- YAML frontmatter
    
- tags
    
- creation dates
    
- runbook type
    
- Django topics
    
- wiki links
    

Now the generated notes become proper Obsidian knowledge-base notes.

---

## Phase 4 — Updating & Searching

This is where the feature gets much more powerful.

The agent could eventually:

```text
"Update my Django ORM note with this information."

"Find my notes about Django authentication."

"Show me everything I've learned about Django middleware."
```

This requires the agent to **read/search the vault**, not merely write files.

---

## Phase 5 — MCP

At this point MCP becomes worthwhile.

Potential architecture:

```text
Django Teacher Agent
        ↓
MCP Client
        ↓
Obsidian MCP Server
        ↓
Obsidian Vault
```

Possible MCP tools:

```text
search_notes
read_note
create_note
update_note
delete_note
create_folder
list_notes
```

This would transform the integration from:

> **"Save my runbook to Obsidian."**

into:

> **"Use my Obsidian knowledge base as part of my Django learning assistant."**

That's a much bigger feature.

# 17. Non-functional requirements

These are easy to forget but important.

### Safety

The integration should **never blindly write to arbitrary paths**.

It should only write inside the configured vault.

For example:

```text
Configured vault:
C:/Users/Tim/Obsidian/MyVault
```

The integration shouldn't allow:

```text
../../some-other-folder
```

to escape the vault.

### Reliability

If Obsidian saving fails:

```text
Runbook generation should still succeed.
```

For example:

```text
Agent generates runbook
        ↓
Obsidian save fails
        ↓
User still receives runbook
        ↓
Agent reports:
"Runbook generated, but couldn't save to Obsidian."
```

The Obsidian integration shouldn't break the core teacher agent.

## ⭐ The most important design decision

**Don't build the entire feature around MCP.**

Build an abstraction:

```python
ObsidianService
```

and initially implement it using:

```text
Python + pathlib + Markdown
```

Then later you can add:

```text
ObsidianService
       │
       ├── LocalFileBackend
       │
       └── MCPBackend
```

That gives your Django Teacher Agent a clean architecture where **MCP is an implementation detail rather than something your entire project depends on**.

And this fits especially well with your existing runbook system: **Phase 1 connects the runbooks you already have → Obsidian; later phases turn Obsidian into an actual searchable learning memory for the teacher agent.**

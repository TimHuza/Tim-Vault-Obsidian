# 1. Project Structure (Top Left)

This is the folder structure of your Django project.

```text
django_ecommerce/
│
├── .github/
│   ├── copilot-instructions.md
│   ├── instructions/
│   ├── prompts/
│   └── skills/
│
├── config/
├── apps/
├── templates/
├── static/
├── media/
├── manage.py
└── README.md
```

Notice that everything AI-related is inside **`.github/`**.

Your Django code (`apps/`, `config/`, etc.) is separate from the files that teach Copilot how to work.

---

# 2. What Each Part Does (Top Right)

This table explains each folder.

## `copilot-instructions.md`

This is the **main instruction manual**.

Example:

```
Use Django REST Framework.

Always use services.

Always create tests.

Use type hints.
```

Copilot reads this for **every request**.

---

## `instructions/`

These are more specific rules.

Example:

```
django.instructions.md

Only applies to Python files.

Use Django ORM.

Don't put business logic in views.
```

Think of them as **department rules**.

---

## `prompts/`

These are reusable workflows.

Example:

```
create-api.prompt.md

1. Create serializer
2. Create view
3. Create URL
4. Create tests
```

Instead of explaining those steps every time, you save them in a prompt.

---

## `skills/`

Skills teach Copilot to act like an expert.

Example:

```
django-security/

Check:

- CSRF
- XSS
- SQL Injection
- Permissions
```

When security is involved, Copilot can use this skill.

---

## `config/`

Normal Django settings.

```
settings.py
urls.py
```

Not AI-related.

---

## `apps/`

Your Django applications.

Example:

```
users/

products/

orders/
```

This is where Copilot writes code.

# 3. Developer Request (Bottom Left)

Suppose you type:

> Create a product review feature.

This is the starting point.

```
Developer

↓

GitHub Copilot
```

Copilot now has to decide how to implement it.

---

# 4. Copilot Loads Context (Purple Boxes)

This is the most important part of the diagram.

Before writing **any code**, Copilot gathers context.

It reads:

```
copilot-instructions.md

↓

instructions/

↓

prompts/

↓

skills/
```

It combines everything into one understanding.

Think of it like a developer opening four documents before coding.

---

# 5. Copilot Understands & Plans (Green Box)

After reading those files, Copilot makes a plan.

The green box says things like:

✔ Understand architecture

✔ Follow coding standards

✔ Plan file structure

✔ Plan tests

It hasn't written any code yet.

It's deciding:

> "I need a model."

> "I need an API."

> "I need tests."

---

# 6. Copilot Generates Code (Blue Box)

Now Copilot finally starts coding.

Because it already knows:

- project rules
    
- Django rules
    
- prompt workflow
    
- expert knowledge
    

it generates code that follows those rules.

## The biggest takeaway

The image shows that **Copilot doesn't just look at your prompt**. Before generating code, it builds context from four sources:

```
Your Request
       +
copilot-instructions.md   ← Project-wide rules
       +
instructions/             ← Technology/file-specific rules
       +
prompts/                  ← Task workflows
       +
skills/                   ← Expert knowledge
       ↓
Generates code that fits your project
```

That's why well-configured Copilot repositories produce code that is much more consistent and aligned with your project's architecture than using Copilot with no repository guidance.
